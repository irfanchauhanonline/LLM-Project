# Song → Artist Matching: Accuracy Evaluation Demo

A small, self-contained sample showing **how I would measure and improve a song-to-artist
matching system**: build a labelled test set, establish a baseline, then make one change at
a time and show before/after numbers, with an honest note on whether each gain is real.

> **The data here is synthetic** (generated by `scripts/generate_data.py`). It imitates the
> problems real catalogues have: missing or inconsistent genre tags, tempo detected at half
> or double speed, speech-to-text errors in lyrics, and artists who look alike on paper.
> The method is the point, not the numbers.

## Run it

```bash
python scripts/generate_data.py   # rebuild the demo data (fixed seed, reproducible)
python evaluate.py                # run all versions; writes results/REPORT.md  (~10s, free)
python evaluate.py --llm          # optional: add an LLM re-ranking step (needs ANTHROPIC_API_KEY)
```

No dependencies for the core evaluation (Python 3.10+). See [`results/REPORT.md`](results/REPORT.md).

## What it measures

| Metric | Meaning |
|---|---|
| **Hit@3 / Hit@5** | % of songs where at least one suitable artist is in the top 3 / top 5 |
| **Hit@1** | % of songs where the #1 result is suitable |
| **MRR** | Mean reciprocal rank: rewards putting the first suitable artist higher |
| **95% interval** | Bootstrap range, because a small test set gives noisy numbers |
| **Sign test** | For each change: did more songs get fixed than broken, beyond chance? |

## How it is set up to be trustworthy

- **Dev / test split.** All tuning happens on the dev songs. Test songs are only used for the
  final report, so the numbers are not flattered by overfitting.
- **One change per version.** Each version adds a single idea, so we know what caused a gain.
- **Per-song before/after.** The report lists songs that newly enter the top 3 *and* songs that
  drop out, so regressions are visible, not hidden in an average.
- **Honest verdicts.** A change that moves only one or two songs is reported as "not conclusive".
- **Failure list.** Songs the best version still gets wrong, as input for the next change.

## Versions

| Version | Change |
|---|---|
| `v0_baseline` | Exact genre-tag overlap (a typical first version) |
| `v1_normalised` | Clean up messy tags: case, punctuation, synonyms (`rnb` → `r&b`) |
| `v2_multisignal` | Add mood, tempo, vocal type and lyric-theme signals |
| `v3_tuned` | Signal weights tuned by grid search on the dev split |
| `v4_llm_rerank` | Optional: an LLM re-ranks v3's top 10 (structured JSON output, cached responses) |

## Applying this to a real system

1. Agree with the domain expert what "suitable artist" means, then label 100–300 real songs
   (several suitable artists per song is fine).
2. Wrap the existing matching code as one ranker function and run it as `v0`.
3. Make changes one at a time (prompt wording, which lyrics/audio features are passed, model
   choice, re-ranking), and track **cost per song and latency** alongside accuracy.

## Layout

```
scripts/generate_data.py   synthetic artists + songs with gold labels
matcher/rankers.py         v0–v3 rankers
matcher/llm_rerank.py      optional v4 LLM re-ranker
matcher/metrics.py         Hit@k, MRR, bootstrap intervals
evaluate.py                runs everything, writes results/REPORT.md
```
